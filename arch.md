# Архитектура платформы сбора и визуализации метрик Metrics Platform

## Пояснительная записка о проделанной работе по проектированию и реализации системы

---

## Введение и общая концепция системы

Разработанная платформа Metrics Platform представляет собой законченное решение для сбора, хранения и визуализации системных метрик в реальном времени. Основная цель проекта заключалась в создании масштабируемой системы мониторинга, способной принимать потоки данных от множества источников, обеспечивать их надёжное хранение во временной базе данных и предоставлять удобный интерфейс для анализа полученных показателей. Архитектура системы построена на принципах микросервисного подхода, что позволяет независимо разрабатывать, тестировать и масштабировать отдельные компоненты системы без влияния на работу других частей платформы.

Фундаментальным решением при проектировании архитектуры стал выбор в пользу разделения ответственности между компонентами системы. Вместо создания монолитного приложения, которое выполняло бы все функции одновременно, было принято решение выделить отдельные сервисы для сбора метрик, их приёма и записи в хранилище, предоставления программного интерфейса для доступа к данным и визуализации информации для конечного пользователя. Такой подход обеспечивает высокую степень изоляции компонентов, упрощает процесс отладки отдельных частей системы и позволяет при необходимости заменять или модернизировать отдельные сервисы без переделки всей платформы целиком.

## Выбор технологического стека и обоснование архитектурных решений

При разработке платформы был выбран язык программирования Python версии 3.14 в качестве основного инструмента реализации всех сервисов системы. Данный выбор обусловлен несколькими важными факторами. Во-первых, экосистема Python предоставляет богатый набор библиотек для работы с сетевыми протоколами, асинхронного программирования и взаимодействия с базами данных временных рядов. Во-вторых, использование единого языка для всех компонентов системы значительно упрощает поддержку кодовой базы, позволяет применять общие подходы к обработке ошибок и логированию, а также облегчает ротацию разработчиков между различными задачами в рамках проекта. В-третьих, современные возможности асинхронного программирования в Python позволяют создавать высокопроизводительные сетевые приложения, способные обрабатывать большое количество одновременных подключений без избыточного потребления системных ресурсов.

В качестве хранилища данных была выбрана база данных InfluxDB версии 2.7, которая представляет собой специализированное решение для работы с временными рядами. Выбор именно этого продукта обусловлен тем, что метрики по своей природе являются данными, привязанными ко времени, и традиционные реляционные базы данных не обеспечивают достаточной производительности при выполнении запросов, которые требуют выборки данных за определённые временные интервалы с последующей агрегацией. InfluxDB предоставляет оптимизированную структуру хранения для временных рядов, поддерживает эффективное сжатие данных и имеет встроенные механизмы для выполнения запросов с группировкой по времени. Кроме того, данная СУБД предоставляет удобный HTTP API для записи и чтения данных, что упрощает интеграцию с другими компонентами системы.

Для контейнеризации всех сервисов системы использована технология Docker с управлением через Docker Compose. Это решение позволяет упаковать каждый сервис вместе со всеми его зависимостями в изолированный контейнер, что гарантирует воспроизводимость окружения при развёртывании системы на различных платформах. Использование Docker Compose даёт возможность описать всю инфраструктуру проекта в виде декларативной конфигурации, где явно указаны зависимости между сервисами, переменные окружения, сетевые настройки и правила проброса портов. Такой подход значительно упрощает процесс развёртывания системы как в среде разработки, так и в промышленной эксплуатации, поскольку для запуска всей платформы достаточно выполнить одну команду.

## Детальное описание компонентов системы и их взаимодействия

### Сервер приёма метрик Metrics Server

Сервер метрик представляет собой низкоуровневый компонент системы, реализующий собственный протокол обмена данными поверх TCP. Выбор именно TCP-протокола для этого компонента обусловлен необходимостью обеспечения минимальных накладных расходов при передаче данных от агентов сбора метрик. В отличие от HTTP, TCP не требует передачи заголовков запроса и ответа для каждой операции записи, что существенно снижает объём передаваемых данных и уменьшает задержку при обработке каждой метрики. Сервер реализован с использованием асинхронной модели программирования на основе asyncio, что позволяет одному процессу обслуживать сотни одновременных подключений без блокировки потока выполнения.

Протокол взаимодействия с сервером метрик предельно прост и включает всего две основные команды: put для записи новой метрики и get для чтения сохранённых данных. Команда put принимает три параметра: имя метрики, её числовое значение и временную метку в формате Unix timestamp. Такая структура команды позволяет клиенту самостоятельно управлять временем измерения, что особенно важно в распределённых системах, где часы на разных узлах могут быть рассинхронизированы. Команда get поддерживает получение как конкретной метрики по имени, так и всех доступных метрик с использованием wildcard-символа, что удобно для первичного ознакомления с имеющимися данными.

Важной особенностью сервера метрик является то, что он не хранит данные в собственной памяти, а сразу после получения каждой метрики записывает её в базу данных InfluxDB. Такое решение устраняет риск потери данных при перезапуске сервиса и снимает ограничения на объём хранимой информации, поскольку все данные сразу попадают в специализированное хранилище. При этом сервер выступает в роли адаптера, который преобразует простой текстовый протокол в формат записи InfluxDB, используя официальную клиентскую библиотеку для взаимодействия с базой данных.

### Программный интерфейс Metrics Client API

Сервис Metrics Client API представляет собой HTTP-обёртку над низкоуровневым TCP-сервером метрик и выполняет роль центрального координационного компонента всей системы. Этот сервис реализован с использованием фреймворка FastAPI, который обеспечивает высокую производительность HTTP-сервера благодаря применению асинхронной модели обработки запросов и автоматической генерации документации OpenAPI. Основное назначение данного компонента заключается в предоставлении унифицированного интерфейса для доступа к данным метрик, который может использоваться как внутренними сервисами платформы, так и внешними клиентами.

Архитектурное решение выделить отдельный сервис для предоставления HTTP API обусловлено несколькими соображениями. Во-первых, это позволяет инкапсулировать логику взаимодействия с TCP-сервером метрик внутри одного компонента, избавляя остальные части системы от необходимости реализовывать низкоуровневый сетевой код. Во-вторых, HTTP API предоставляет более богатый набор возможностей по сравнению с простым TCP-протоколом, включая поддержку структурированных запросов с параметрами, различные форматы представления данных и стандартные механизмы аутентификации и авторизации. В-третьих, наличие промежуточного слоя между клиентами и сервером метрик даёт возможность реализовать дополнительную функциональность, такую как кэширование, агрегация данных и применение алгоритмов сглаживания.

Одной из ключевых особенностей данного сервиса является реализация endpoint'а для потоковой передачи данных с использованием технологии Server-Sent Events. Этот механизм позволяет клиентам установить постоянное соединение с сервером и получать обновления метрик в реальном времени без необходимости периодически опрашивать сервер. В обработчике потокового endpoint'а реализована логика сглаживания данных с помощью скользящего среднего, вычисляемого с использованием библиотеки Pandas. Это решение устраняет резкие кратковременные пики на графиках визуализации, делая отображаемую информацию более читаемой и понятной для анализа.

Сервис также предоставляет endpoint для получения статистического анализа метрик, который вычисляет основные показатели распределения данных, такие как среднее значение, стандартное отклонение, минимальное и максимальное значения, а также определяет тренд изменения метрики с помощью линейной регрессии. Для вычисления тренда используется библиотека NumPy, которая эффективно решает задачу аппроксимации данных полиномиальной функцией. Все вычисления выполняются асинхронно в отдельном потоке, чтобы не блокировать обработку других запросов во время тяжёлых вычислений с большими наборами данных.

### Агент сбора метрик CPU Monitor

Агент CPU Monitor отвечает за сбор системных метрик с хоста, на котором он запущен, и передачу этих данных в центральный сервис через HTTP API. Данный компонент реализует модель периодического опроса системных счётчиков с настраиваемым интервалом измерения, что позволяет балансировать между детализацией собираемых данных и нагрузкой на систему. Агент способен собирать широкий спектр метрик, включая процент использования каждого ядра процессора, общую загрузку CPU, текущую частоту процессора, а также показатели использования оперативной памяти.

Важной особенностью агента является поддержка модульной архитектуры с возможностью подключения различных компрессоров данных. Компрессор представляет собой компонент, который применяет алгоритмы сжатия к сырым данным перед отправкой на сервер, что позволяет уменьшить объём передаваемой информации и снизить нагрузку на сеть. В текущей реализации доступен компрессор "none", который передаёт данные без изменений, однако архитектура допускает добавление новых алгоритмов сжатия, таких как усреднение значений за интервал или передача только дельт изменений.

Агент разработан с учётом требований надёжности и устойчивости к ошибкам. В случае возникновения проблем при сборе метрик или отправке данных агент не завершает свою работу, а фиксирует ошибку в логе и продолжает выполнение следующего цикла измерений. Такая стратегия обеспечивает непрерывность мониторинга даже в условиях нестабильной работы сети или временной недоступности центрального сервиса. Кроме того, агент корректно обрабатывает сигнал прерывания работы, что позволяет аккуратно завершить текущий цикл измерений и освободить ресурсы перед остановкой процесса.

### Веб-интерфейс Web Dashboard

Веб-дашборд представляет собой клиентское приложение, работающее полностью в браузере пользователя и предоставляющее интерфейс для визуализации метрик в реальном времени. Приложение реализовано как автономный веб-компонент на основе стандарта Web Components, что обеспечивает высокую степень инкапсуляции и переиспользуемости кода. Компонент подключается к серверу через Server-Sent Events и автоматически обновляет графики при поступлении новых данных, создавая эффект живого мониторинга без необходимости ручной перезагрузки страницы.

Для отрисовки графиков используется библиотека Chart.js в сочетании с адаптером Luxon для работы с временными метками. Этот выбор обусловлен тем, что Chart.js предоставляет широкий набор возможностей для настройки внешнего вида графиков при относительно небольшом размере библиотеки, что важно для быстрой загрузки веб-страницы. Библиотека Luxon обеспечивает корректную обработку временных зон и форматирование дат, что критично для правильного отображения временных рядов пользователям из разных регионов.

Архитектура веб-дашборда следует принципу разделения ответственности между HTML-разметкой, стилями и логикой поведения. HTML-файл содержит минимальную разметку с объявлением кастомного элемента metrics-dashboard, который инкапсулирует всю функциональность приложения. JavaScript-код компонента управляет подключением к потоку данных, созданием и обновлением графиков, обработкой пользовательского ввода для выбора метрик и настройки параметров отображения. Такой подход позволяет легко интегрировать дашборд в другие веб-приложения или использовать его как самостоятельное решение.

### Интерактивная тетрадка Marimo Dashboard

Компонент Marimo Dashboard представляет собой альтернативный интерфейс для анализа метрик, реализованный в виде интерактивной тетрадки на платформе Marimo. В отличие от классического веб-дашборда, который ориентирован на непрерывное наблюдение за показателями в реальном времени, тетрадка предоставляет более гибкие возможности для исследовательского анализа данных с возможностью применения сложных алгоритмов обработки и визуализации. Marimo выбран в качестве платформы благодаря своей реактивной модели выполнения, которая автоматически пересчитывает зависимые ячейки при изменении входных параметров.

Тетрадка организована в виде последовательности ячеек, каждая из которых выполняет определённую функцию в процессе анализа данных. Первые ячейки содержат импорт необходимых библиотек и определение параметров подключения к API метрик. Следующие ячейки создают элементы управления интерфейсом, такие как селекторы для выбора метрик, ползунки для настройки временного окна и интервала обновления. Отдельные ячейки отвечают за получение данных от сервера, их обработку и построение визуализаций с использованием библиотеки Plotly.

Особенностью данной тетрадки является использование двухпанельной компоновки графиков, которая позволяет одновременно отображать большие наборы метрик, распределяя их между верхней и нижней панелями. Для каждой метрики строится временной ряд с цветовой кодировкой для различения линий на графике. Дополнительно к графикам тетрадка отображает таблицу со статистическими показателями по каждой метрике, включая среднее значение, стандартное отклонение, тренд, минимальное и максимальное значения. Эта информация помогает быстро оценить общее состояние monitored системы и выявить аномалии в поведении метрик.

## Сетевая архитектура и организация взаимодействия между сервисами

Все сервисы системы объединены в единую виртуальную сеть Docker network с именем metrics-net, которая обеспечивает изолированное пространство для межсервисного взаимодействия. Использование отдельной сети позволяет сервисам обращаться друг к другу по именам контейнеров без необходимости пробрасывать порты наружу, что повышает безопасность системы и упрощает конфигурацию. Только те сервисы, которые должны быть доступны извне, имеют проброшенные порты на хост-машину, в то время как внутреннее взаимодействие происходит исключительно внутри сети Docker.

Схема взаимодействия между сервисами построена по принципу восходящего потока данных. Агент CPU Monitor инициирует соединение с сервисом Metrics Client API и периодически отправляет собранные метрики через HTTP POST запросы. Metrics Client API, получив данные, устанавливает соединение с сервером Metrics Server по TCP протоколу и передаёт метрики для записи в базу данных. Metrics Server, в свою очередь, подключается к InfluxDB и выполняет запись данных в соответствующую таблицу. Таким образом, данные движутся от источника к хранилищу через цепочку промежуточных компонентов, каждый из которых добавляет свой уровень обработки.

Для чтения данных используется обратный поток запросов. Веб-дашборд и Marimo тетрадка обращаются к Metrics Client API с HTTP GET запросами для получения исторических данных или установления потокового соединения. Metrics Client API запрашивает данные у Metrics Server через TCP протокол, а тот выполняет查询 к InfluxDB с использованием языка Flux. Полученные результаты проходят через цепочку компонентов в обратном направлении и в конечном итоге отображаются пользователю в виде графиков и таблиц. Такая архитектура обеспечивает чёткое разделение ответственности и позволяет каждому компоненту фокусироваться на своей задаче.

## Стратегия развёртывания и конфигурирования системы

Система спроектирована с поддержкой нескольких сценариев развёртывания, что обеспечивает гибкость при использовании в различных средах. Основной производственный сценарий предполагает запуск всех сервисов в контейнерах Docker через Docker Compose одной командой. Конфигурация каждого сервиса задаётся через переменные окружения, которые могут быть определены в файле .env в корне проекта или заданы непосредственно в docker-compose.yml. Такой подход позволяет хранить конфиденциальные данные, такие как учётные записи базы данных, отдельно от кода конфигурации и легко менять настройки без модификации файлов образа.

Для сценариев разработки предусмотрена возможность запуска отдельных сервисов в изоляции или в комбинациях. Например, разработчик может запустить только API сервис и сервер метрик для отладки логики обработки данных, оставив базу данных и агенты сбора на потом. Также поддерживается гибридный режим, когда часть сервисов работает в контейнерах Docker, а другая часть запущена непосредственно на хост-машине в режиме отладки с автоперезагрузкой при изменении кода. Это особенно полезно при разработке веб-интерфейса, где требуется мгновенное отражение изменений в браузере.

Конфигурация зависимостей между сервисами настроена таким образом, чтобы гарантировать правильный порядок запуска. Сервис Metrics Server зависит от InfluxDB и не начнёт работу до тех пор, пока база данных не сообщит о готовности через health check. Сервис Metrics Client API зависит от Metrics Server, а агенты и дашборды зависят от API. Такая цепочка зависимостей предотвращает ситуации, когда сервис пытается подключиться к ещё не готовому зависимому компоненту и завершается с ошибкой.

## Обеспечение надёжности и отказоустойчивости

При проектировании системы особое внимание было уделено вопросам надёжности и устойчивости к сбоям. Каждый сервис реализован с учётом возможности временной недоступности зависимых компонентов. Например, если сервер метрик теряет соединение с InfluxDB, он продолжает принимать данные от клиентов и возвращает ошибку, но не завершает свою работу. При восстановлении соединения сервис автоматически возобновляет запись данных без вмешательства оператора. Аналогично, агент сбора метрик продолжает работать при временной недоступности API, буферизируя данные в памяти до момента восстановления связи.

Механизм health check, реализованный для базы данных InfluxDB, позволяет системе автоматически обнаруживать проблемы с хранилищем и информировать зависимые сервисы о невозможности выполнения операций записи. Docker Compose использует результаты health check для принятия решений о перезапуске контейнеров и уведомлении других сервисов об изменении статуса зависимости. Это обеспечивает самовосстановление системы при временных сбоях инфраструктуры.

Логирование во всех сервисах настроено на вывод информации в стандартный поток вывода, что позволяет централизованно собирать логи через средства Docker и анализировать поведение системы в целом. Сообщения об ошибках содержат достаточный контекст для диагностики проблем, включая имена компонентов, параметры соединений и детали исключений. Такой подход упрощает поиск и исправление ошибок как в процессе разработки, так и при эксплуатации системы.

## Заключение и перспективы развития системы

Разработанная платформа Metrics Platform представляет собой законченное решение для мониторинга системных метрик, сочетающее в себе современный технологический стек, продуманную архитектуру и удобные интерфейсы для визуализации данных. Применение микросервисного подхода позволило создать гибкую систему, которую можно легко адаптировать под изменяющиеся требования и масштабировать по мере роста нагрузки. Разделение ответственности между компонентами обеспечивает независимость разработки и упрощает поддержку кодовой базы.

Архитектурные решения, принятые в ходе разработки, такие как использование специализированной базы данных временных рядов, применение асинхронной модели программирования и организация потоковой передачи данных, обеспечивают высокую производительность системы при умеренном потреблении ресурсов. Поддержка различных сценариев развёртывания делает платформу универсальным инструментом, который может быть использован как для локального мониторинга отдельных серверов, так и для создания распределённых систем наблюдения за инфраструктурой.

Перспективы развития системы включают добавление поддержки дополнительных типов метрик, таких как показатели дисковой подсистемы, сетевой активности и состояния приложений. Расширение функциональности агентов сбора позволит мониторить не только локальные ресурсы, но и удалённые узлы через безопасные каналы связи. Интеграция с системами оповещения даст возможность автоматически реагировать на критические изменения метрик и предотвращать развитие инцидентов. Добавление механизмов долгосрочного хранения данных с понижением детализации со временем обеспечит возможность ретроспективного анализа и выявления долгосрочных тенденций в поведении системы.
